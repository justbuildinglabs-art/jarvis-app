SYS // VOICE ENGINE EVALUATION

ELEVENLABS VS LOCAL

Should the HUD's voice come from the cloud instead of the two models running on your machine? This compares speed and cost against the current stack — Kokoro for speech, faster-whisper for listening.

Read this first
Every number here is published by a vendor or already written in this repo's docs. Nothing was benchmarked on this machine. Vendor latency figures are best-case marketing numbers measured in the vendor's own datacentre; the repo's local figures describe an NVIDIA GPU that this Mac does not have. Treat the shape of the comparison as sound and any single number as approximate.

00 The finding that matters most

ElevenLabs was already wired into this codebase — and removed on 2026-06-12. The evidence is still in the source: lib/tts.ts and lib/stt.ts both carry a comment saying the cloud fallback was taken out, app/api/speak/route.ts still describes an audio/mpeg response and quotes Flash v2.5's 75ms first byte, and lib/voiceClient.ts still refers to Scribe for transcription. Where the cloud call used to be, the code now throws a configuration error.

So this is not a new decision. It is a reversal of a reversal — and whatever drove the original removal is not recorded anywhere in the repo or its git history (a single squashed commit). Worth recovering that reasoning before spending money to undo it.

The 75ms bar is not a number you would ever experience. The CPU row is derived, not measured. The README states CPU runs "~4x slower" than the ~250ms/sentence GPU figure, which lands around 1,000ms. Separately, CLAUDE.md puts the whole voice pipeline at ~2.7s end-to-end on CPU. Both are repo claims, neither was verified here.

Segments in the top bar: ~130ms transcription, ~20ms routing, ~270ms to first spoken audio. The README quotes the same loop as a 175–500ms range.

This is the chart that actually argues for the cloud. On your hardware the local loop is roughly six times slower than the GPU numbers this project's docs advertise — and a cloud TTS leg at ~150ms would be genuinely faster than a local CPU leg at ~1,000ms. The speed case for switching is real, but it is a case against CPU inference, not against local inference.

Assumptions are stated so you can re-run them: 30.4 days/month, and each push-to-talk clip about 5 seconds for the transcription side. Replies are capped at 900 characters server-side and 800 client-side in this codebase, so ~200–300 characters is a realistic average for the short spoken answers the router produces.

Pay-as-you-go beats a subscription at these volumes. Typical use is ~456,000 characters a month; the $22/mo Creator plan includes 220,000 and the $99/mo Pro plan 440,000 — so the metered rate (~$23) is cheaper than the plan that would actually cover it.

One unverified risk. A third-party guide claims ElevenLabs bills a 1,000-character minimum per request. Nothing on ElevenLabs' own pricing or docs pages confirms this, so it is excluded from the figures above — but if it were true, ~200-character HUD replies would each bill as 1,000 and the real cost would be roughly 5× the numbers shown. Check a live invoice before committing.

04 What the swap would actually cost to build

The charts above hide the engineering. The seams are clean, but three specific properties of the current design would break if you routed around the local server carelessly.

  • The easy part is genuinely easy. Three function bodies — speak(), ttsStatus(), transcribe() — each with exactly one caller. Everything downstream is untouched if the return contract holds.
  • There is no provider abstraction to slot into. The stack is hardcoded to Kokoro down to the TypeScript type, which literally reads engine: "kokoro". A switchable build means writing that seam first.
  • Streaming is the real risk. Speech starts fast because the Python server splits the reply into sentences and ships the first one immediately under a fake-length WAV header. Using ElevenLabs' non-streaming endpoint would replace "first audio in ~270ms" with "first audio once the entire reply has been generated" — losing the exact property the interface was designed around.
  • The orb would go flat if wired directly. Its animation reads amplitude from a WebAudio analyser fed by the audio element. Point that element at a cross-origin URL and the browser feeds the analyser silence. The cloud audio must keep being proxied through /api/speak.
  • The wake word cannot move to the cloud. It runs whisper in-process inside the Python server and never touches the swappable transcription seam. Switching STT to the cloud leaves two different engines on the two input paths — and the Python server still has to run, so nothing is actually simplified.
  • The response format is hardcoded. The TTS seam always reports audio/wav no matter what the upstream actually sent; ElevenLabs returns MP3. Chrome usually sniffs past that, Safari may not.
  • Reveal timing is calibrated to the current voice. Document cards are scheduled off a constant of 13 characters per second, measured from Kokoro at speed 1.0. A different voice desynchronises the cards from the speech until it is re-measured.

Switching also falsifies a claim this project makes about itself: the architecture brief states "No telemetry, no third-party voice cloud." That line would have to change, and the README's "voice never leaves your machine" with it.

06 Reading of the evidence

The strongest argument for switching is not cloud-vs-local — it is GPU-vs-CPU. Your slow voice is a hardware symptom: the same code answers in ~270ms on the GPU this project was built against, and ~1,000ms here. ElevenLabs at ~150ms would fix the symptom for around $23/month at typical use, plus a network dependency, an outbound copy of everything you say, and the loss of offline operation.

Before paying for that, two cheaper experiments are worth running: measure the actual local latency on this Mac — every figure here is published rather than observed, and the real number may be better or worse than the derived ~1,000ms — and find out why the previous ElevenLabs integration was removed, since someone already made this trade once and reversed it.
